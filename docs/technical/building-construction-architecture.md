# Building & Construction — Technical Architecture

**Design spec:** [/docs/design/game-systems/world/building-construction.md](../design/game-systems/world/building-construction.md)

How we build the freeform construction system: geometry foundations, data model, pathfinding, room detection, task integration, rendering, UI, and the phasing. Player-facing behavior lives in the design spec; this doc is the how.

## 2. Architecture Decisions

### D1: Integer-quantized committed geometry

UI and previews work in float world meters. Geometry that gets **committed** (a placed vertex, a closed polygon) is quantized to integer millimeters (`int64` per axis). Rationale:

- Exact vertex equality: merging snapped points is `==`, not epsilon comparison. Epsilon merging is not transitive (A~B, B~C, but not A~C) and produces inconsistent topology; this failure mode is the recurring theme in robust-geometry literature.
- Exact predicates: orientation and intersection tests on integer coordinates are exact with wide multiplication (128-bit intermediates). No epsilon zoo, no Shewchuk machinery.
- Clipper2 (see D2) operates on int64 natively; quantization is its robustness model, not an extra step.
- Deterministic across platforms, which matters for the multiplayer future.

1 mm resolution is far below any gameplay constraint (smallest constraint is the 0.3 m opening margin) and invisible at render scale.

### D2: No new dependencies — geometry built in-house, concepts borrowed

We roll our own core systems; the Tessellator already did this (monotone decomposition with concepts borrowed from Lyon, no library taken). Geometry follows the same pattern. The decisive fact: we need a narrow slice of what libraries like Clipper2 offer, and the hard substrate is something we must build anyway.

- **Triangulation:** the existing Tessellator covers runtime-generated polygons (foundation fills, room tints). Our generated geometry is well-formed by construction (D4 invariant), so no second triangulator is needed.
- **Booleans:** the only consumers are foundation Add (union of two simple polygons), blueprint Subtract (difference), and overlap rejection. Implemented as **arrangement insert + face classification** on the same planar-graph / face-extraction core room detection needs (D6): insert both rings' segments, split at intersections with exact integer predicates, walk faces, classify by containment, take the result boundary. One core powers booleans and rooms. We can also reject any result that violates constraints (holes, slivers) instead of repairing it, which removes most of what makes general-purpose clippers hard.
- **Offsetting (wall bands):** straight segments only, miter joins. The 30° minimum-angle constraint bounds miter length (≤ ~3.9× half-thickness), and minimum clearance prevents band self-overlap, so the general algorithm's hard cases (arcs, self-intersection trimming, collapsing loops) are unreachable. A small custom implementation.
- **Concepts borrowed from Clipper2** (the library itself not adopted): integer coordinates as the robustness model, miter limit with square fallback, and a simplification pass after boolean ops as the second line of defense against slivers.

Risk acknowledged: hand-rolled booleans are the riskiest in-house piece; coincident-edge unions are the classic failure mode and Add-mode hits them constantly (snapped shared edges are the normal case, not the exception). Mitigation: exact integer predicates make coincidence testable as equality, the input domain is narrow (two simple polygons, editor-validated), and this code gets the densest test suite in the feature, with shared-edge and shared-vertex cases enumerated first. Record the considered-and-rejected libraries (Clipper2, earcut.hpp, CGAL, CavalierContours) in `library-decisions.md`.

### D3: New library `libs/geometry`

Pure math, depends only on `foundation` (and the two new third-party libs). Contents:

- `Vec2i64` + quantize/dequantize helpers
- Exact predicates: orientation, segment-segment intersection, point-in-polygon, point-to-segment distance
- Polygon ops: signed area, winding, self-intersection test, min interior angle, min vertex spacing, edge-to-edge clearance (the constraint primitives from the design spec)
- Planar graph / half-edge structure with face extraction (the shared core: room detection in D6, boolean ops in D2)
- Boolean ops (union/difference/overlap) via arrangement + face classification, per D2
- Straight-polyline offsetting with miter joins (wall bands) + post-op simplification pass

Unit-tested in isolation; this library is where geometric correctness lives, so it gets the densest test coverage of the feature.

### D4: Data model — topology graph as source of truth, ECS for gameplay state

Structures are both topology (vertices, segments, junctions, attachment points) and gameplay objects (HP, blueprint progress, selection, tasks). One representation can't serve both well, so:

**`ConstructionWorld`** (new, owned alongside the ECS world) holds the topology:

```
ConstructionWorld
├── foundations:  FoundationId → { ring: [Vec2i64], material, state, entity: EntityID }
├── vertices:     VertexId     → { pos: Vec2i64, segments: [SegmentId] }
├── segments:     SegmentId    → { v0, v1: VertexId, material, thicknessPreset,
│                                  hostFoundation: FoundationId, state, entity: EntityID }
├── openings:     OpeningId    → { segment: SegmentId, t: float (param along segment),
│                                  type, material, state, entity: EntityID }
└── rooms:        RoomId       → { face: [SegmentId], area, entity: EntityID }  (derived)
```

- **Stable IDs.** A T-junction snap splits a host segment into two; both halves get new IDs but openings re-attach by parameter range, and the ECS entity of the demolished/split piece is handled explicitly. Stable IDs are what make door/window attachment survive topology edits (the lesson from Tiny Glade's "five brainstorming sessions for doors": openings interact with every wall invariant, so attachment must be a first-class modeled relationship, not a position lookup).
- **ECS mirror.** Every foundation, segment, and opening also exists as an ECS entity carrying gameplay components: `StructureBlueprint { required[], delivered[], workTotal, workDone }`, `Structure { kind, graphId }`, HP, selection metadata. Bidirectional maps connect `graphId ↔ EntityID`. The graph answers "what is connected to what"; the ECS answers "what state is this thing in" and lets tasks, selection, vision, and rendering treat structures like any other entity. The `delivered[]` / `recordDelivery` / `materialsComplete()` metered-deposit model is shared with crafting: a crafting station provisions its recipe bill of materials by the same mechanism (deposit metered to remaining need, no leftover ever). See [Crafting & Material Provisioning](./crafting-provisioning-architecture.md).
- **Invariant: the editor never commits invalid topology.** All constraint checks (min angle, spacing, clearance, self-intersection, no X-crossings) run at draw time and reject the candidate point with a reason. This is the Manor Lords pattern (reject degenerate plots with feedback, never repair), and it is what keeps every downstream consumer (face extraction, nav rasterization, band generation) simple. Repair algorithms are explicitly out of scope.
- **Serialization-friendly by construction:** POD records, stable integer IDs, versioned container. No save system exists yet; this shape costs nothing now and avoids a painful retrofit.

### D5: Navigation — interface contract only; nav itself is its own spec

Navigation is its own system (`libs/sim/nav`) with its own spec, deliberately **not** designed here. Two things are fixed in this doc; everything else is deferred to that spec:

**1. Sequencing.** Navigation is not a build-order prerequisite for construction. Foundations, the construction loop, drawing tools, rendering, rooms, and openings are all buildable and testable without it. What nav gates is walls *shipping as gameplay*: until it lands, built walls don't block movement. The construction epics proceed; nav is scheduled independently and must land before walls are player-facing.

**2. The contract construction provides and consumes.** Construction is designed so the nav implementation choice doesn't leak into it:

- Built walls publish their **exact band polygons** (integer coords, from D2 offsetting) as obstacles, carrying their **stable structure IDs** so navigation can belief-filter per agent (memory-aware pathfinding: agents only "see" structures they've discovered). Water and other blockers publish similarly. Blueprints publish nothing.
- Openings publish **portals** (position on a segment, width, passability).
- Construction consumes a **reachability query** (for goal validity: can any builder reach this work slot?) and a **nav version counter** (so MovementSystem replans when construction changes the world).
- The **pathing clearance constant** lives in construction config and is shared; nav honors it, the editor enforces it, and the design spec's solid-or-passable guarantee is what makes the two ends meet.

The nav spec is [Pathfinding Architecture](./pathfinding-architecture.md). It commits to the vector-native direction (dynamic constrained-Delaunay navmesh consuming our exact wall-band polygons directly, no rasterization), inside a four-tier model (planet hex graph → chunk components → CDT navmesh → physical agents). The contract above is what construction publishes into it; its P4 phase is the gate for walls shipping as gameplay.

### D6: Room detection — half-edge face extraction, incremental

Rooms are faces of the planar graph formed by **built** wall segments (centerlines). Algorithm (standard, cp-algorithms construction): at each vertex sort outgoing half-edges by polar angle, link twins to the angularly-next edge, walk the links to enumerate faces; faces with negative signed area are outer faces, the rest are rooms. Openings live on segments and do not break edges, so a doored wall still encloses.

The editor invariants (no X-crossings, T-junctions pre-split, min angle/spacing enforced) remove everything that makes arrangements hard; with integer coordinates the whole extractor is exact and small. CGAL-class machinery is unnecessary precisely because D4 forbids invalid input.

- **Trigger:** wall segment transitions to built, or a built segment is demolished. Each change of the construction version re-runs `detectRooms` over the whole world (`RoomDetectionSystem::update` calls `reconcile()`), then matches the new rooms to the previous records.
- **Rooms with holes:** a room is an outer ring (counter-clockwise) minus zero or more holes (each clockwise, as the arrangement walks it). A wall loop standing free inside a room, touching none of its walls, is a separate wall group; its outline becomes a hole of the smallest room that contains it, and only that one, so in a three-level nest each room holds just the room directly inside it. The inner loop is its own room. A room's area is net of its holes (a 1 x 1 m room inside a 5 x 5 m room leaves the outer room 24 m²), and its representative point lies strictly inside the ring and outside every hole (unless the scan finds no such point, for a room only millimetres tall, in which case the old point is kept unverified). Containment is `construction::pointInRoom`: inside the ring and outside every hole, with any ring or hole edge reading as the boundary. The rooms overlay tessellates the ring and its holes together, so every floor is tinted once, outlines the holes as well as the ring, and picks a clicked room with the same test: a click strictly inside a room selects it, which makes the inner room of a nest the one selected, and a click on a boundary two rooms share goes to the higher room id.
- **Room identity:** matched against the previous records in passes, each record inherited by at most one new room. First, a room whose outer ring is a record's stored ring (the same vertex cycle) keeps that record, so building or removing a room inside another never renames the outer room. Then a room inherits a record whose stored representative point is strictly inside it; then, for a point a new wall now runs through, one whose point is on its boundary (the first room in canonical order that still has none takes it, so one side of a divider keeps the name). When a room holds several stored points (a merge), the largest stored area wins, then the lowest id. Anything left unmatched is a new room with a new id and name. When several walls change in one update so that a room closes round another room's stored point while that room's outline also changes, the inner room takes the name (WOR-875).
- **Failure feedback:** when a wall completes and almost-closes a loop, nothing happens silently (the Prison Architect confusion). Cheap heuristic for later UX polish: surface near-misses in the rooms overlay.

#### Enclosed shade (WOR-743)

Player-facing behaviour, and the four proposed defaults it rests on (awaiting the owner's confirmation): design spec, Rooms > Enclosed Look. In short: every room's floor gets a flat, hard-edged, translucent black fill of one fixed strength, drawn in the committed-construction pass, so it sits under colonists, furniture, and the player visibility cover.

**Today (main at 30320bc1).** There is no enclosure flag and nothing to add one to: every bounded face of the built-wall centrelines is a room (`detectRooms`, `libs/sim/construction/RoomDetection.cpp`), only segments in state `Built` are fed to the arrangement, and openings live on segments, so a doored or windowed wall still encloses. `ecs::RoomDetectionSystem` (`libs/sim/ecs/systems/RoomDetectionSystem.{h,cpp}`, priority 59) polls `ConstructionWorld::version()`, re-runs `detectRooms` on a change, and keeps `RoomRecord`s (`rooms()`); a new room fires `onRoomFormed`, which `GameScene.cpp` wires to the "Room formed" toast. The highlight pulse the design spec promises on room formation is not implemented. There is no floor system (the foundation's fill is the floor), and no roof, shadow, or indoor tint anywhere; `docs/design/main-game-ui-design.md` states the game has no roofs. On main a `RoomRecord` has a ring and no holes, and `world_sim::RoomOverlay::render` (`apps/world-sim/scenes/game/world/rooms/RoomOverlay.cpp`) re-tessellates every room's screen-space ring each frame.

**Prerequisite: nested rooms (WOR-512).** On `feat/WOR-512-nested-rooms`, not yet on main, a room is an outer ring (CCW) minus holes (each CW): a wall loop standing free inside a room is a hole of the smallest room containing it and a room of its own, and `RoomRecord` gains `holes`. Its `RoomOverlay` keeps one world-space `TessellatedMesh` per room (`RoomFill`, `syncFills`), built by the salal tessellator's multi-contour `Tessellate(std::span<const VectorPath>, ...)` with the default nonzero fill rule (`TessellatorOptions::useNonZeroFillRule`), which cuts the CW holes out of the CCW ring, and re-tessellates a room only when its ring or holes differ from the cached copy. The shade is specified on that model and lands after it.

**Input.** `RoomDetectionSystem::rooms()`: per record, `roomId`, `ring`, `holes`. The shade polygon of a room is its ring with its holes cut out, so in a nest every floor is covered exactly once: the outer room's shade stops at the inner room's walls, and the inner room's shade covers the inner floor. Shades never overlap, which is what keeps nested rooms from reading darker. The ring is the wall centrelines; the wall bands (keys 60 to 62) and openings (63, 64) draw over the shade's outer half-thickness, so on screen it ends at the walls' inner faces without an inset.

**Geometry, shared with the overlay.** The tessellation the WOR-512 overlay caches moves out of `RoomOverlay` into one cache both draws read, so each room is tessellated once however many things draw it (one path):

- `worldview::RoomFillCache` (`libs/world-view/world/rendering/RoomFillCache.{h,cpp}`): per room, `roomId`, an `origin` (the ring's first vertex, as in WOR-512), the mesh in metres relative to it, and the ring's world bounding box for culling. `sync(const ecs::RoomDetectionSystem&)` is O(1) when nothing changed: it compares `RoomDetectionSystem::roomsRevision()` with the revision it last synced, and only on a difference walks the records, re-tessellating the rooms whose ring or holes changed and dropping fills whose room is gone. A room that fails to tessellate gets an empty mesh and a `LOG_DEBUG`, as in WOR-512, and draws neither tint nor shade.
- `RoomDetectionSystem::roomsRevision()` is new: a counter `reconcile()` increments when the record set changes or any record's `ring` or `holes` change. A construction version change that leaves every room as it was (a blueprint placed, a foundation built) does not move it.
- `RoomOverlay` takes a `const RoomFillCache*` in its `Args` and deletes `RoomFill`, `fills`, and `syncFills`. `GameScene` owns the one cache and hands it to both draws; whichever draws first in a frame calls `sync`, the second finds it current.

**Renderer.** `worldview::RoomShadeRenderer` (`libs/world-view/world/rendering/RoomShadeRenderer.{h,cpp}`), so world rendering stays in `world-view`, which already links `sim` and `assets`; `sim` gains nothing that touches the renderer. It holds the cache and the `RoomDetectionSystem`, and `render(const world::WorldCamera&, int viewportWidth, int viewportHeight, float pixelsPerMeter)` syncs the cache, culls each fill's box against the camera's visible rect (grown by 2 m, the margin `DrawingSystem::renderCommitted` uses), projects the mesh's vertices to the screen as the overlay does, and submits one `Renderer::Primitives::drawTriangles` per visible room in the shade colour at that room's `shadeAlpha`, key 53. `GameScene::render` calls it between `m_drawingSystem->renderCommitted(w, h)` and the `Renderer::Primitives::flush()` that follows it; `DrawingSystem` stays unaware of rooms.

**Draw order.** `GameScene::render` at HEAD, with the keys each draw uses. Keys order draws only within a flush (salal `Primitives.h`: a higher key paints over a lower one between sort barriers; worldsim sets no barrier in this pass).

1. Terrain: `ChunkRenderer::render`.
2. Committed construction, `DrawingSystem::renderCommitted`: foundation blueprint base 50, progress fill 51, outline 52; walls (and fallback centrelines) 60, wall progress fill 61, wall edges 62; opening fills 63, opening detail and lines 64. **The shade goes here, at 53.** Then `Primitives::flush()`.
3. Entities: `EntityRenderer::render`, groundcover and every Y-sorted upright (colonists, creatures, furniture, trees, loose items). They draw after the flush, so they cover the shade and are never darkened by it.
4. Player visibility cover: `VisibilityCoverRenderer::render`, out-of-sight tint key 30 (alpha `kSeenDimAlpha`, 0.5) and unseen fill key 31. It covers the shade like any other ground.
5. Post-entity draws in the same flush as the cover: drawing preview (898 to 910), terrain polygon overlay (40), rooms overlay (tint 56, outline 57, label 58; selected room 100), nav and vision overlays, selection indicator and move marker (100), placement ghost (1000). The rooms overlay paints over the shade, as the design spec asks.

**Config.** `assets/config/construction/rendering.xml` gains a `<RoomShade>` element: `color` `#000000FF` (rgb only; the alpha comes from `fillAlpha`) and `fillAlpha` 0.15. `assets::RoomShadeStyle { StyleColor color; float fillAlpha = 0.15F; }` joins `RenderingConfig` as `roomShade` (`libs/assets/assets/ConstructionRegistry.h`), loaded in `ConstructionRegistry::loadRendering` beside the other styles. A `fillAlpha` outside 0 to 1 logs a warning and keeps the default, the way a malformed colour does today.

**Lighting hook.** The strength is a per-room value the renderer reads, `float RoomShadeRenderer::shadeAlpha(const ecs::RoomDetectionSystem::RoomRecord&) const`, which in version 1 returns `roomShade.fillAlpha` for every room. Lighting replaces that body (an enclosed room with no lights or windows goes quite dark, windows and lights lighten it) and changes nothing else: geometry, cache, draw order, and key stay. Nothing is added now for lighting beyond that one function.

**Deliberately not built.** Soft edges, gradients, or any pixel effect (version 1 is hard vector edges; soft edges wait for a later style pass); an inner shadow band along the walls (needs a general polygon inset `libs/geometry` does not have); a cast shadow outside the walls; roofs; any raster, grid, or texture for the shade, render-only or not (every shade is a vector triangle mesh); darkening entities; the formation pulse.

**Cost.** Per frame: one revision compare, then per room a box test and, for a room in view, one projection of its mesh vertices (a tessellated ring plus holes has as many vertices as the ring and holes together) and one batched triangle draw. Per room change (a room forms, changes shape, or goes): one multi-contour tessellation per changed room, on the main thread at the first draw after the reconcile, shared with the overlay. On main the overlay re-tessellates every room each frame; WOR-512 already caches that, and this shares that cache. Nothing has been timed. What could move is the committed-construction pass in views that hold rooms; the PR's `Perf:` line names that, and the capture is scoped to such a view if the scripts' views contain one.

### D7: Construction lifecycle — goal source into the task system

Construction is a **goal source** in the sense of the planned Goal-Driven Task Generation refactor (`/docs/technical/task-generation-architecture.md`): blueprints create goal-level tasks; reservations stay item-level.

- **`ConstructionSystem`** (ECS system, logic band): watches blueprint entities and emits goals through their lifecycle:
  1. *Clear:* query `SpatialIndex` for entities on the foundation footprint (position inside the ring, the box as broad phase) → chop/mine/haul-away goals. Blueprint blocked until clear. As built: harvestables hold the site and are cleared by a colonist; when the foundation enters construction the rest of what is on the footprint (grass, stones, rocks, loose piles) is taken off it, so it is built on bare ground (`docs/technical/task-claims.md`, "Build-site clear").
  2. *Deliver:* blueprint advertises a material manifest (computed from geometry × material config). The blueprint entity carries a delivery inventory (reuses `Inventory` + a restricted accept list); standard haul chains (`Chain_PickupDeposit`) bring materials. Site-staged materials render as piles.
  3. *Build:* when the manifest is complete (and, for walls, the host foundation is built), emit build goals. `Build` action already exists (`needsHands=true`); `ActionSystem` ticks `workDone += rate(skill) × dt` and marks render progress dirty. Multi-builder (as built for foundations): N builder spots spaced round the ring, 0.5 m in from their own edge (along the bisector at a corner, on the ring where that would not be inside), N from `constraints.xml` scaled by area and capped by a minimum spacing; each builder holds one spot as a numbered slot claim and stands where the nav mesh gives for it, and once every spot is held the Build reads Reserved for the rest (`docs/technical/task-claims.md`, "Build and Deconstruct"). Walls and openings have no spots and no cap.
  4. *Demolish:* mirrored `Deconstruct` work; refund percentage from config; cascade ("Demolish building") queues openings → walls → foundation as ordered goals.
- **Ordering dependency:** the goal-driven refactor is in flight as draft PR #115, which already includes a `BuildGoalSystem` — the exact hook this design plugs into. If it hasn't landed when construction starts, construction rides the current registry the way Haul does today and migrates with everything else.
- **Pathfinding contract:** builders must *reach* work slots; goal validity includes a region-level reachability check, which is exactly what D5's regions make cheap.

### D8: Rendering — existing draw system, new mesh source

Structures are tessellated vector meshes like everything else and render through the **existing pipeline**: the baked world-space base-shader path the render perf overhaul just optimized (cached world-space vertex buffers, sub-region culling, no per-frame tessellation). No new renderer, no new shader path. The new code is mesh **generation** only.

- **Mesh source:** structure geometry comes from generators (pattern emitters, wall bands) instead of SVG templates, but the output is the same `TessellatedMesh` shape the pipeline already consumes. Open integration question, resolved with profiling during Epic C: inject structure geometry into the per-chunk entity bake, or give structures their own baked buffer set on the same path. Either way it's the existing machinery. One genuinely new requirement: a draw-order guarantee that floors and wall tops render above terrain and below colonists/items.
- **Procedural patterns as ordered element emission.** Each material defines an element emitter (plank runs, stone courses) that fills a polygon or band with discrete vector elements, deterministically seeded per structure. Elements are emitted **in build order** (the design spec's progressions: sills → joists → decking; corners → courses → infill), and the index buffer is laid out in that order. **Construction progress then renders a prefix of the index buffer** (`drawElements` with count = f(workDone/workTotal)). No rebaking during construction, no animation system, and progress is deterministic and save-stable by construction.
- **Wall bands and junctions.** Per-segment band = centerline offset by half thickness (Clipper2). At junctions, segment bands are trimmed against a computed junction polygon (miter for 2-way joins within miter limit, bevel/fan for 3+ way), so chains read as one continuous wall top. This junction-resolution step is custom code in `libs/geometry`; offsetting each segment independently and overlapping them is the naive fallback but produces visible double-draw seams with translucent blueprint rendering, so trimming is the plan of record.
- **Blueprint state:** dashed outline + faint fill, rendered from the same geometry with a blueprint style, via the structure pass (not GhostRenderer, which stays cursor-preview only).
- **Drawing preview:** the in-progress polygon/polyline (rubber band, fill preview, guides, origin halo) renders through `Primitives` immediate mode, like GhostRenderer does today.

### D9: Doors/windows — parameterized procedural assets

Requirement: one asset per opening type, adapting to wall thickness and material. The asset system has a Lua procedural-generation path with static params; extend it with **call-time parameters**:

- Generator signature gains a params table: `generate(seed, { thickness, materialPalette })`.
- Cache key extends from `defName` to `(defName, thicknessPreset, material)`. Cardinality is small and bounded (opening types × thickness presets × materials), so every combination is cached as a normal template; no shader work, no per-instance vertex stretching.
- Material palettes come from the construction material config (D10), so a wood door and wood wall agree on color.

Rejected: vertex-shader stretch axis + palette swap (more moving parts for the same small variant set), and per-combination authored assets (explicitly forbidden by the design spec).

### D10: Config — `assets/config/construction/`

Follows the `assets/config/work/` pattern: XML, loaded at game start, validated fail-fast by `ConfigValidator` extensions.

- `materials.xml`: per material per structure kind — cost rate, work rate, HP, insulation, flammability, beauty, speed modifier (foundations), thickness presets (walls), pattern parameters (element emitter type, palette, seeds).
- `constraints.xml`: pathing clearance, min corner angle, min vertex spacing, segment clearance, min/max area, max points, opening margins, refund percentage, builder caps.

Cross-validation: every material referenced by a thickness preset exists; opening types reference valid materials; constraint values are internally consistent (e.g., clearance ≤ segment clearance).

### D12: Snap engine (helpers, guides, lengths)

Player-facing behaviour: design spec, Foundations > Drawing and Foundations > Snapping and guides, and UI & Selection > Drawing Settings and Key guide. Alignment is one formulation in which the world axes are one guide source of three, every helper sits behind a player setting, and common lengths and length rounding run as one length step. The rectangle tool's corner snap is D13, the settings' storage D14, the key guide D15, and the look D16. The values were tuned in an interactive prototype outside the repository; every case in the test list below passes in it.

**The entry points.** `libs/sim/construction/SnapEngine.cpp`: `snap()` tries origin-close (3+ points; it ignores `freeform`), foundation vertex, foundation edge (squared by a shape guide), the guides, the angle step, then the raw cursor. `snapWall()` tries, in order, the chain's first point (kind `Origin`, once the chain has `kMinClosingWallChainPoints` points and the cursor is within the close radius; skipped under `freeform`), wall endpoint, foundation vertex (inset), wall segment interior (squared), foundation edge (inset, squared), the guides and the angle step (both skipped under `freeform`), then the raw cursor. The guides, the angle step, and the raw cursor are `snapToHelpers`, which both entry points end with. `snapAngle` reads `points.back()` (its callers check `!points.empty()`) and returns nothing, which leaves the raw cursor, in two cases, a cursor at zero distance from that point and an increment of zero or less; otherwise it snaps the direction from it to the nearest `angleIncrementDegrees` step off the previous segment (off +x for the first), keeping distance, and a half step rounds up (`floor(x + 0.5)`, as the prototype rounds); it has no capture window, so past those two cases it is the unconditional fallback once no guide has caught. The guides come first, so a world-axis line within 0.3 m cannot pre-empt the 90-degree turn on a rotated shape: the shape's own perpendicular ranks ahead of it.

#### The engine

One pure function per tool: `SnapEngine::snap()` (Freeform foundation tool), `SnapEngine::snapWall()` (wall tool), and the free function `snapRectangleCorner()` (D13; `RectangleSnap.h`). Inputs: the pointer (world metres), the placed points, the existing geometry (`ConstructionWorld`'s foundations, blueprints included, with their placement order; in the wall tool also its wall vertices and segments), the snapping config (`SnappingConfig`), and, in a `SnapInput`, the player's drawing aids (`DrawingAids`, the engine's part of the Drawing Settings; D12 and D14), `freeform` (Alt held), the wall half-thickness (integer millimetres), and the origin-close radius (widened with zoom by `DrawingSystem`). Output: the snapped point, what it landed on, up to two guides to draw, what the length step did, the kept common lengths (so labels can show `=`), and whether a click closes. The engine is const and keeps nothing between calls but reusable working storage (per thread, cleared and never shrunk). `DrawingSystem` builds a `SnapEngine` in `handleMouseMove` and `handleWallMove` when its snap memo misses; the memo's key is the tool, the cursor, the aids, the world version, `freeform`, the zoom, the wall's thickness preset, the wall's host, and the edit target, and the placed points are compared beside it. A second pure helper, the free function `cornerAngles()` (`CornerAngles.h`, one `CornerAngleInput`), computes the angle readout from the placed points and the snapped point; it snaps nothing.

#### Guides

A **line** is a node (a point) and a direction, compared modulo 180 degrees; directions come in **pairs**, a direction and its perpendicular. The engine builds nodes, directions, and the lines below; captures lines near the cursor; merges near-duplicates; forms crossings; ranks every candidate with one key.

**Nodes.**

- Shape points: `points`. A foundation has at most `maxPoints` (32, constraints config; the validator refuses more). A wall chain has no such cap, so its lines use `points[0]` and its most recent `maxPoints - 1` points. The wall tool passes the constraints' `maxPoints` in `SnapInput`; the Freeform tool's snap does not read it.
- Committed corners, only when `alignToExistingBuildings`. Freeform tool: foundation ring vertices. Wall tool: each foundation ring vertex at `outerFaceFlushCorner(ring, index, wallHalfThicknessMm)` (the function adds the 2 mm safety, `kFlushInsetSafetyMm`, itself), where a perimeter wall's centerline turns, plus wall vertices. Those within `guideRangeMeters` of the cursor are taken nearest first, at most `guideCornerLimit`; ties fall to `foundations()` order and ring index, then `vertices()` ascending id. Each corner remembers its structure (its foundation, or the wall segments at that vertex) and its edge directions (a foundation corner: toward the previous ring vertex, then toward the next; a wall vertex: along its segments in ascending id). Using the inset corner in the wall tool keeps a foundation corner's guides on the perimeter wall's centerline instead of half a wall thickness outside it, where they would run parallel to the wall vertex's own guides and fight them.

**Directions.**

- Shape first: `points[0]` to `points[1]`, once there are two points.
- Shape previous: `points[n-2]` to `points[n-1]`, once there are three points and it differs from the first by more than `guideDirectionToleranceDegrees` (mod 90 degrees).
- Nearby, only when `alignToExistingBuildings`: committed edges whose closest point is within `guideRangeMeters` of the cursor (Freeform tool: foundation ring edges; wall tool: those plus wall segment centerlines), zero-length edges skipped, walked by that distance, ties by foundation id and ring index, then segment id (two edges that meet at the corner nearest the cursor are exactly as near, and the tie goes to ring order; the tuned prototype's answer there is rounding noise). An edge within `guideDirectionToleranceDegrees` (mod 90 degrees) of the world axes or of a direction already kept is skipped; the first `nearbyGuideDirectionLimit` are kept, each with the structure that supplied it. A skipped duplicate still counts for corners: a kept direction also takes every structure in range that has an edge within `guideDirectionToleranceDegrees` (mod 90 degrees) of it, so two parallel sheds both get the lines. Blueprints count; they are what the player is lining up with.
- World: +x.

**Lines, the closed list.** Nothing else generates a line. Generation order is this list, then node order, then a pair's direction before its perpendicular; for item 3 it is nearby direction first (nearest direction first), then node (the previous point, then the corners).

1. The shape first pair through every shape point. `DrawnShape`. Needs `guidesFromShape`.
2. The shape previous pair through `points.back()`. `DrawnShape`. Needs `guidesFromShape`.
3. Each nearby pair through `points.back()` (when there is one) and through the committed corners of every structure in range that has an edge within `guideDirectionToleranceDegrees` (mod 90 degrees) of it, the one that supplied it included. `NearbyStructure`. Needs `alignToExistingBuildings`. The line bound is unchanged, since the corners are capped at `guideCornerLimit` however many structures share a direction. Case: two parallel sheds at 37 degrees; shed B's edge is nearer and supplies the direction, shed A's edge is skipped as a duplicate, and A's corners still get 37-degree lines, so the player can line up with A's face.
4. The world pair through every shape point and every committed corner (there are corners only with `alignToExistingBuildings`). `WorldAxes`. Needs `guidesFromWorldAxes`.

Left out on purpose: the shape's directions through committed corners (a building parallel to the shape brings its own direction through its own corners, and no worked case needs more), nearby directions through shape points other than the previous one, and directions from shape edges other than the first and previous.

**Capture.** A line is captured when the cursor is within `guideToleranceMeters` of it. A `DrawnShape` line that passes within 1 mm of `points.back()` or (with two or more points) of `points[0]` is also captured when the direction from that point to the cursor is within the angle window of the line (mod 180 degrees, so a cursor behind the point catches too); the window is `angleIncrementDegrees / 2` while `tieAngleWindowToStep` holds, else `guideAngleWindowDegrees`. The test is geometric, not by node: the first edge's own line is generated through `points[0]` (and through `points[1]`, then dropped as a duplicate by the merge), and it still catches by angle from `points[1]` while that is the previous point. A single line's snapped point is the foot of the perpendicular from the cursor.

The window through the previous point is the angle step's own, so the 0, 90, 180, and 270-degree turns off the previous edge are caught exactly where `snapAngle` caught them, and come back as `GuideLine` with a marker. The window through `points[0]` catches the closing corner: on the 30-degree rectangle below, the cursor (-1.6, 3.8) is 0.51 m off the guide through `points[0]` (outside the 0.3 m tolerance) but 7.2 degrees off it as seen from `points[0]`, so the guide is captured and the crossing forms. Nearby and world lines are distance-only, so they never crowd out the other 15 degree steps. The angle step governs only when no line is captured; its result keeps kind `Angle`.

**Merge.** Captured lines are walked in rank order (source, then shape point before committed corner, then generation order). A line within `guideDirectionToleranceDegrees` (mod 180 degrees) of a kept line, and closer to it than the merge distance at the kept line's foot of the cursor, is dropped into that kept line, which records the dropped line's node. The merge distance is `guideToleranceMeters` while `tieMergeDistanceToTolerance` holds, else `guideMergeDistanceMeters`. So a committed corner's line 0.25 m from the shape's own parallel line does not take over when the cursor drifts nearer to it.

**Crossings.** Only with `guideCrossings`. Each pair of kept lines that meet at the crossing minimum angle or more (mod 180 degrees; `angleIncrementDegrees` while `tieCrossingAngleToStep` holds, else `guideCrossingMinAngleDegrees`) gives its intersection, kept when it lies within `guideCrossingRadiusMeters` of the cursor, unless both lines pass within 1 mm of a node that one of them was generated through: its own node, or the node of a line merged into it. Two lines through a shared node always cross on it, which would otherwise make each node a magnet out to the crossing radius: with the shape at 30 degrees, a cursor 0.5 m from `points[1]` at 112 degrees is 0.070 m from the 120-degree line and 0.187 m from the 90-degree world line through `points[1]`, and their crossing is `points[1]` itself. With the rule it lands on the 120-degree line. The rule is by generating node, not by any node on both lines: read the second way it would also drop a rectangle's closing corner that falls on an existing building's corner, which the lines through `points[2]` and `points[0]` reach without being generated there; kept, it still snaps there when the cursor is 0.4 to 0.52 m off, past the 0.4 m vertex snap. The angle minimum drops near-parallel crossings, which hold the point through a dead zone (a 30-degree guide and a 31.5 degree nearby line are both captured over about 23 m of their length).

**Ranking.** One lexicographic key, smaller wins. With `priorityRule` `sourceFirst` (the default):

1. The best source among the candidate's lines (`DrawnShape` < `NearbyStructure` < `WorldAxes`)
2. Crossing before single line
3. The best line's node: shape point before committed corner
4. Distance from the cursor to the snapped point (differences within 1e-9 m are ties)
5. Generation order: a single line by its own; a crossing by its earlier line, then its later

A crossing's best line is the higher-ranked of its two by source, then node, then generation. So a `DrawnShape` single line beats a `NearbyStructure` crossing, and the crossing of the shape's own two lines (the rectangle's closing corner) beats every single line and every crossing whose best line is not a shape line; it is level with any other crossing led by a shape line until distance decides. There is no key for a crossing's second line (the other line's source); the ranking is the tuned prototype's. With `priorityRule` `closest` the key is crossing before single line, then distance, then generation; it exists for comparison in tuning (the same cursor in `GuideDrawnShapeBeatsCloserWorldAxis` goes to the world line under it).

**Squaring on existing edges.** In `snap()`'s edge rule and in `snapWall()`'s wall-segment and foundation-edge rules, the hit is found as above, then, unless `freeform` or `guidesFromShape` is off: each captured `DrawnShape` line, in generation order, that meets the hit's line (the foundation edge; in the wall tool the inset edge line; the wall segment's centerline) at the crossing minimum angle or more, at a point on the edge (end points included; strictly interior for a wall segment, so it stays a T-junction) within `edgeSnapRadiusMeters` of the cursor, is a candidate, and the nearest to the cursor is returned instead of the foot (generation order on ties). Kind and hit ids are unchanged (`Edge`; `WallSegment` with `hitSegment`), and `guides[0]` carries the line with its marker. Case: `points` (0, 0), (5.196, 3.000), a foundation edge along y = 6, cursor (3.580, 5.8) on the 120-degree guide 0.2 m short of the edge. The foot is (3.580, 6.000), whose edge direction is 88.3 degrees off the first edge's, leaving a 91.69-degree interior corner at `points[1]`; the squared point is (3.464, 6.000), 0.23 m from the cursor, on the edge, 90 degrees. The vertex rules stay ahead and unchanged; a corner beating a guide is intended.

**Landing on the first point.** With three or more points, a guide result (a single line's foot, or a crossing) within the close radius of `points[0]` snaps to `points[0]` and is returned as `Origin`, so the click closes; its guides still draw. The radius is the one `SnapInput` carries (the game widens it with zoom), and the config's `originCloseRadiusMeters` only when it carries none. In `snapWall()` the same rule applies once the chain has `kMinClosingWallChainPoints` points (the same three). In both entry points the first-point close runs before the guides, so a guide result lands on the first point only when the cursor is outside the close radius. No length step follows. Case: closing the 30-degree rectangle with the cursor at (0.214, 0.47), 0.516 m from `points[0]`, just outside the origin-close radius. The shape's perpendicular through `points[0]` (which also runs through `points[3]`) is captured by angle, 6.5 degrees off as seen from `points[3]`, and its foot lands 0.30 m from `points[0]`, so without this the preview shows a too-short closing edge and only `DrawingSystem`'s rescue-close (`closeRescueRadiusMeters`) would save the click.

**Right-angle marker.** For each returned guide, the edges at its node are tested in order: for a shape point, the shape's edge into it (toward the point before), then out of it (toward the point after, when there is one); for a committed corner, its edge directions in the order above. The first within `guideDirectionToleranceDegrees` of perpendicular to the guide sets `rightAngle` and `rightAngleEdgeDirection` (unit, from the node along that edge). The marker sits at the guide's `from`. A guide parallel to the first edge gets a marker too when the edge into its point is perpendicular to it, as at `points[2]` of a rectangle; through `points[0]` or `points[1]` it gets none, since the only edges there are the first edge itself.

**Where it sits.** The guide step (`alignToGuides`, which `snapToHelpers` runs for both entry points) comes after the geometry rules and before the angle step. Real geometry stays ahead (zero-gap adjacency is a hard rule). The world axes are line list item 4, with the guide tolerance (`guideToleranceMeters`, 0.3 m); the wall tool's foundation corners are at their inset points.

#### Common lengths

Only with `commonLengths` and not `freeform`. Computed once per move, before the rules; used by the length step.

1. **Entries.** With `commonLengthSourceShape`, each edge between consecutive placed points (owner: the shape; it ranks newest of all; owner distance 0). With `commonLengthSourceBuildings`, every foundation, each with its owner distance (the cursor's distance to its nearest ring edge) and its placement order: each ring edge, or in the wall tool, while `commonLengthWallsReadInsetFoundation` holds, each edge between consecutive inset corners (`outerFaceFlushCorner(ring, index, wallHalfThicknessMm)`). In the wall tool, also each wall segment, owned by the chain it was drawn in, which its placement order identifies (below). A chain's owner distance is its nearest segment's. The wall tool's inset corners are computed in double (the same function as `outerFaceFlushCorner`), so the edges between them are exact to the millimetre however far the building is from the origin. An owner past the range is skipped unread (unless `commonLengthAllBuildings`): a foundation whose ring's bounds lie past it, or a chain segment whose bounds do; that segment then does not count toward the chain's owner distance, and a chain with no segment in reach lends nothing.

**Placement order.** There is no separate counter: the order is `ConstructionWorld::version()` read at the start of the commit. `version_` is a monotonic `uint64_t`, never reset, and every successful `commitFoundation`, `commitExtension`, and `commitSegment` bumps it, so no two commits read the same value; values are sparse (state and entity changes bump it too), which is harmless, since only their order is used.

- *Stored fields.* `Foundation::placementOrder` and `WallSegment::placementOrder`, both `std::uint64_t`. A save format has to carry both and restore `version()` above every stored value, or a building placed after a load ranks older than the ones loaded.
- *Foundations.* `commitFoundation` records `version_` before its bump. So does `commitExtension`: an extension is a placement, and ranks as its own building while it is pending. `mergeExtension` removes the extension record and the target keeps its own order (a merge reshapes the target; the player placed nothing new then). Add and Subtract in place on a blueprint (`addToFoundation`, `subtractFromFoundation`) keep the foundation's order.
- *Walls.* A chain is many `commitSegment` calls, each bumping the version, so the order is passed in: `commitSegment` takes a `std::uint64_t placementOrder` parameter from its caller, and `DrawingSystem::commitWallChain` reads `version()` once before its first segment and passes that value for every segment of the chain. One committed chain shares one value, which is how a segment knows its chain. Segments the new pair is split into (drawn through an existing vertex) take the chain's value; the two halves of an existing segment that a T-junction splits keep that segment's value. Walls re-hosted by a merge keep theirs.
- *Ctrl+click edge fill* is a chain of its own: it reads `version()` before its commit.
- *Tests, benches, and dev verbs.* Every `commitSegment` caller passes a value: `DrawingSystem::devCommitWalls` (the `/api/dev` wall path) reads `version()` once per call, so a dev-stamped loop is one chain; tests (through `SnapWorld::addWall` in `SnapTestFixtures.h`) and the two benches (`NavigationSystem.bench.cpp`, `PlayerVisibilitySystem.bench.cpp`) pass `version()` the same way, or an explicit value when a case is about order. The dev foundation path goes through `commitFoundation` and gets its order there.
2. **Filter.** An entry shorter than `commonLengthMinimumMeters` is dropped. A building or chain entry whose owner distance is over `commonLengthRangeMeters` is dropped, unless `commonLengthAllBuildings`.
3. **Grouping.** Entries are walked newest owner first (the shape, then the highest placement order), then nearest owner, then generation order. An entry within `commonLengthMergeMeters` (plus 1e-9 m) of an existing group's length joins the first group created that is within that distance; otherwise it starts a group with its own length. A group's length is its first entry's.
4. **Ranking.** Groups sort by newest member (descending), then member count (descending), then nearest owner (ascending), then length (ascending). The first `commonLengthMaxCount` are kept, and never more than `kMaxCommonLengthCount` (16), the most the result reports.
5. **Catch along a line.** Given the segment's start `start` (`points.back()`), a line (origin `origin`, unit direction `direction`), and the current point `current` on it: for each kept group of length `length`, let `foot` be the foot of `start` on the line and `offset = |start - foot|`. If `offset > length` the length is out of reach. Otherwise the target is whichever of `foot + direction * sqrt(length^2 - offset^2)` and `foot - direction * sqrt(length^2 - offset^2)` is nearer `current`, and the slide is `|target - current|`. A group catches when its slide is at most `commonLengthCatchMeters`; of those, the smallest slide wins, then the better group rank.

#### The length step

`refine(origin, direction, current, allowRounding)`, applied where the point can still slide along a line:

1. With no point placed, or `freeform`, nothing.
2. A common length that catches (above) moves the point to its target. Kind unchanged; the result records `CommonLength`, the length, what it is measured from (`lengthFrom`), and the group's edges (for the ticks).
3. Else, when `allowRounding`, `roundLengths` is on, and `lengthIncrementMeters` > 0: `length = floor(|start - current| / increment + 0.5) * increment` (a half increment rounds up); if `length` > 0 and reachable on the line (as in the catch), the point moves to that target and the result records `Rounded`.
4. Else the point stays.

Where it runs:

- **A single guide through the previous point** (its node within 1 mm of `points.back()`): `refine(node, direction, foot, true)`.
- **A single guide through any other point**, with `lengthRoundingOnGuides` `guideDistance` (the default): `refine(node, direction, foot, false)`; if no common length caught and rounding is on, the distance along the guide from its own node rounds instead: `along = (foot - node) . direction`, `rounded = floor(|along| / increment + 0.5) * increment`, and if `rounded` > 0 the point is `node + sign(along) * rounded * direction`, recorded as `RoundedAlongGuide`. This runs with no point placed too. With `segmentLength`, `refine(node, direction, foot, true)` instead.
- **A crossing**: fixed. With `commonLengthBeatsCrossing` on, `refine` runs from the cursor's foot on each of the crossing's two lines with `allowRounding` false; if either catches, the smaller slide wins (the best line on a tie), and the result becomes a `GuideLine` on that line alone at the common length.
- **The angle step**: `refine(points.back(), stepDirection, point, true)`.
- **The raw cursor**, while `commonLengthAfterRawCursor` holds and the cursor is off the previous point: `refine(points.back(), unit(cursor - points.back()), cursor, true)`.
- **Never** after the close, a corner, an edge (squared or not), a wall endpoint or segment, or a guide result that landed on the first point.

#### What is drawn

The result carries what the preview needs; D16 has the look.

- **Guides.** `guideCount` guides (2 for a crossing, 1 for a single line, the angle step, a squared `Edge` or `WallSegment`, and an `Origin` from a single guide; 2 for an `Origin` from a crossing), each from its node to the snapped point, with its source, marker, and `distanceFromNodeMeters` (`|to - from|`). The angle step's guide is the ray from `points.back()`, source `DrawnShape` (`WorldAxes` for the first segment), no marker, no distance label. A guide's stroke draws only where it lies more than a pixel from the segment being drawn (the previous point to the snapped point), since dots that close would bead the solid line. Every guide ends at the snapped point, the segment's end, so the stroke runs from its node to where the guide first comes within a pixel of the segment. A guide through the previous point (the angle step's ray included) has nothing left: no stroke of its own, only its right-angle marker if it has one. A guide from an older node along the segment keeps its stroke to a pixel short of the previous point, and its distance label sits beside that stroke; a guide a fraction of a degree off the segment stops where it comes within the pixel.
- **A crossing dot** at the point for `GuideCrossing`, drawn over the snapped-point marker's dot.
- **The segment label**, beside the segment's middle or at the snapped end (D16 has the rule): `|point - points.back()|` to `guideDistanceDecimals` places and " m", with " =" and the accent colour when the length step recorded `CommonLength` or the length is within `commonLengthMergeMeters` of a kept group, the two compared in whole millimetres and the merge distance itself included, as the engine's grouping includes it.
- **Common-length marks**, when the length step recorded `CommonLength`: a tick across the segment at the snapped end, and on every edge of the matched group a faint highlight and a double tick at its middle.
- **Guide distance labels** (`guideDistances` on): for each guide whose `relation` is not `AngleStep` and whose stroke draws with at least 40 px of it on screen, `distanceFromNodeMeters` the same way, with " =" on a kept-group match. The label draws only with the stroke, so a guide the segment covers entirely (one through the previous point, or one whose node lies on the segment) has none; the segment label reads that length. Placed beside the middle of the part of the stroke on screen, while its text stays the guide's whole distance from its node, its plate 7 px off it (the text 10 px at an Interface size of 100%) on the side away from the segment's middle (the other side when that leaves the screen). When the segment's middle is within half a pixel of the stroke's line, as it is for a guide along the segment, neither side is away from it, and the label takes the side facing up the screen, or the left one when the guide is within about 11 degrees of vertical. If its plate overlaps the segment label, an earlier guide label, the snapped-point marker out to its ticks, the close halo while it is drawn, the wall tool's snap-target ring, or the box the preview keeps clear (a rejected edit's reason), it shifts along the guide by its own width plus 8 px, first back toward its node, then forward, alternately, up to six times, never past either end of the stroke's part on screen (a shift that would is cut to that end), and is dropped when no spot along it is clear.
- **The angle readout** (`angleReadout` on, not `freeform`, not the rectangle tool), from the free function `cornerAngles(CornerAngleInput)` (`CornerAngles.h`), given `points`, the snapped point as `cursor`, `closes` when the next click closes the shape (the tool's own close, `DrawingFeedbackInput::clickCloses`: an `Origin` result or the near-start rescue close, the same close the halo and the close verdict follow), `tool`, `closingReachMeters = 2 * originCloseRadiusMeters`, and `squareToleranceDegrees = 0.5 * 10^-angleReadoutDecimals`, where `originCloseRadiusMeters` is the radius passed in `SnapInput`: the game widens the close radius at low zoom, so the closing reach widens with it (the prototype has no such widening). The path is `points` plus the snapped point, or `points` alone when the click closes; a rescue close counts as the click closing, though the snapped point is not on `points[0]`. It reads as a polygon when it has three or more vertices and the tool is the Freeform tool or the chain is closing. The corner at `points.back()` is always read; the corner at `points[0]` too when there are three or more points, the path reads as a polygon, and the click closes or the snapped point is within the closing reach of `points[0]`. A polygon corner is the interior angle: the sweep from the edge toward the previous vertex to the edge toward the next, taken the other way round when the path's inside does not lie along its bisector at the vertex itself, which is when a ray from the vertex along the bisector crosses the path's other edges an even number of times. For a simple polygon that is the side its orientation gives, so a nearly straight corner of a thin shape reads its interior angle, under 180 degrees. A path whose points are collinear has no inside, and its corner reads the plain angle between its edges: 180 degrees straight on, 0 folded back. An open-chain corner is the unsigned angle between its two segments. A corner with an edge under 1 mm is skipped; a corner within the square tolerance of 90 degrees draws the right-angle marker; any other draws an arc and its degrees (D16 has the look, including when a guide's marker stands in for the corner's and when a short edge leaves the corner unmarked). Nothing shows with fewer than two points.

#### Units, determinism, cost

Positions are float world metres, like every other snap. The table's distances are world metres, the same at every zoom, with two exceptions: the origin-close radius, which `DrawingSystem` floors at `originHaloMinRadiusPx` on screen (`effectiveOriginCloseRadiusMeters()`) and passes in `SnapInput`, and `doubleClickDistancePx`, which is in logical pixels. Float spacing is under 0.5 mm below 4096 m from the world origin and doubles with each power of two beyond it; within that range a guided corner is exact to float rounding (about 0.25 mm), and the millimetre quantization on commit (D1) adds up to 0.5 mm per axis, so a guided right angle over a 3 m edge is square to a few hundredths of a degree. Farther out the error grows with the spacing. Tests compare positions to 1e-3 m unless they say otherwise. Snapping runs on the local cursor only and the command carries the quantized point, so float differences between machines never reach sim state. On one machine the result is a pure function of the inputs: every walk is over `foundations()`, `segments()`, `vertices()` (ascending id) or `points`, never an unordered container, and every tie has a fixed winner. Among guides a tie falls to the generation order (Ranking, key 5). The foundation corner and edge snaps keep the last of equal-distance hits (`<=` in `nearestFoundationCorner` and `nearestFoundationEdge`), and so does the rectangle tool's adjacency (D13), which calls the same two functions. The wall endpoint and wall segment snaps keep the first (strict `<`, so the lowest id).

Per cursor move the line list holds at most 298 lines: 66 from the shape (32 points by one pair, plus the previous pair), 136 nearby (4 directions by the previous point and up to 16 corners, by a pair: 4 x (1 + 16) x 2), and 96 world (48 nodes by a pair). Each is one point-to-line distance. After the merge at most 48 lines stay captured (14 directions, at most three parallel lines per direction inside the band twice the tolerance wide, plus the 6 shape lines through `points[0]` and `points.back()` that catch by angle), and crossings are formed among those; in practice two or three. Common lengths add one entry per edge of the shape and of each building in range (walls too, in the wall tool), grouped against at most a few dozen groups; in practice a few buildings, well under a hundred entries. Finding the corners, nearby edges, and length entries is a walk over the committed foundations and walls, as `nearestFoundationEdge` is; a foundation whose bounds lie past the range is skipped whole. The studies work in per-thread storage that is cleared and never shrunk, and the result's guides, matched edges, and kept lengths are fixed-size arrays, so the engine's own storage is reused and its results are fixed-size; with common lengths on, the length study calls `std::stable_sort`, which may allocate a temporary buffer in the standard library. None of it runs on the sim or render hot path.

### D13: Rectangle tool

Player-facing behaviour: design spec, Foundations > Drawing > Rectangle tool. The default foundation tool, for the player who wants a square building and nothing else.

In the code: `snapRectangleCorner()` and `rectangleFromCorners()` with their tests (`RectangleSnap.test.cpp`); the tool in `DrawingSystem` (`handleRectangleMove`, `handlePress`, the release in `handleClick`, `cancelPress`, `renderRectanglePreview`, `pickFoundationTool`), its size label, grid cross, rings, and snapped-point marker in `DrawingFeedback`, the tool picker in `ConstructionConfigStrip`, and the input routing in `WorldPointer` (`drawingPointerAction()`), which `GameScene` acts on.

- **A mode of the foundation tool.** `ToolKind::FoundationRectangle` beside the polygon foundation tool (`ToolKind::Foundation`) in `DrawingSystem`. It shares material, validation, commit, and the config strip with the polygon tool; only point placement differs.
- **Choosing it.** The Build menu's Foundation entry opens the foundation tool last picked this session, Rectangle the first time; the construction strip's tool picker switches between Rectangle and Freeform. In code: `activateFoundationTool()` keeps meaning the freeform polygon tool, since `DrawingSystem.test.cpp` calls it and then clicks polygon points; `activateRectangleTool()` opens the rectangle tool; `DrawingSystem` holds the session's last pick (set by either call, read by `lastFoundationTool()`), and `GameScene`'s `onStructureSelected("foundation")` calls whichever that pick is, through `DrawingSystem::pickFoundationTool()`. The picker (`ConstructionConfigStrip`, two cards built as the material cards are, shown while a foundation tool is on, no hotkey and no keyboard focus) calls `pickFoundationTool()` too: switching tools drops the shape in progress, as the prototype's tool buttons do, and picking the tool already on leaves it as it is. No dev verb activates a foundation tool: `/api/dev/foundation` commits through `ConstructionWorld::commitFoundation` directly.
- **Corner snap.** `snapRectangleCorner(world, snapping, aids, cursor, freeform)` (a free function in `RectangleSnap.h`), pure like the others; first that applies wins. It returns the point and a `RectangleSnapKind` (`None`, `Vertex`, `Edge`, `Grid`), the rectangle's own kind, not a `SnapKind`. Under `freeform`: the raw cursor, `None`. Else, while `rectangleAdjacencySnaps` holds: `nearestFoundationCorner` within `vertexSnapRadiusMeters` (`Vertex`); else `nearestFoundationEdge` within `edgeSnapRadiusMeters` (`Edge`), and when that edge is axis-aligned (its ends equal in y, or in x, within 1e-9 m) the foot's free coordinate also rounds to the grid, kept only if the rounded point is still on the edge. Those two queries are the freeform tool's own, so both tools agree on what an existing corner is, and equal-distance vertices or edges keep the last found (`<=`). Else the grid point, each coordinate `floor(value / spacing + 0.5) * spacing` (`Grid`), halves rounding up. The grid is anchored at the world origin; the spacing is `aids.rectangleGridSpacingMeters`, the Drawing Setting (1.0 or 0.5), and a spacing of zero or less leaves a coordinate unrounded.
- **Input.** A press places the first corner (when none is placed). A release farther than the config key `doubleClickDistancePx` (4 logical pixels, the space `InputEvent::position` is in) from that press places the second (a drag); a release within it leaves the first corner waiting, and with a corner waiting the next click places the second on its release. A second corner level with the first in either axis, the pointer still on the first corner included, makes no rectangle: the release places nothing and refuses nothing, no toast and no red, and the first corner waits. A release that ends no press the tool saw (its press landed on the interface) does nothing. A release over the interface or outside the window, or a press whose release is lost with the window's focus, commits nothing: the press is forgotten, and the first corner, the press's own included, waits for a later click. Esc, right-click, or Backspace drops the first corner; a second Esc exits the tool, as for the other tools. Add and Subtract on a foundation stay freeform.
- **Delivering the press.** Every drawing tool's left press and release go through the routing that tells the world from the interface; only the Rectangle tool takes a press. `drawingPointerAction()` (`scenes/game/world/WorldPointer.h`) decides, from the input (a press, a release, or a frame with the left button up), the button, where the pointer is, whether the pointer is with the tool (`pointerWithTool()`, below), the drawing tool on, and whether a press is pending, what `GameScene` does: deliver the press (`DrawingSystem::handlePress(...)`, which places the first corner when none waits and records the press), deliver the click (`handleClick`), cancel the press (`cancelPress()`), cancel the tool (`cancel()`, a right release), ignore it, or pass a release on to placement and selection when no drawing tool is on. Where the pointer is comes from `pointerTarget()`, beside it: on the world, on the interface (hit-tested in ui px, the pointer divided by the Interface size's scale), or outside the window; `update()` uses the same test for the previews. The Rectangle tool takes a left press on the world, with the pointer with the tool, and nothing else; its left release off the world, or while the pointer is not with the tool, cancels the press. A release the interface takes never reaches `handleEvent`, so `update()` asks `drawingPointerAction()` about each frame with the left button up, which cancels a pending press. Every other tool sees only its releases: a left release on the world is its click, and one that reaches `handleEvent` off the world (over a part of the interface that does not take it, or outside the window), or while the pointer is not with the tool, places nothing.
- **The tool pauses off the window.** `pointerWithTool()` (`WorldPointer.h`) decides whether the drawing tools follow the pointer: it is in the window (the window system's word, and inside the window's bounds) and the window has the focus. `GameScene` keeps both in a `WindowPresence` (`WorldPointer.h`), which follows the events the scene receives, one at a time: `PointerEnter` and `PointerLeave` move the pointer in and out, `FocusGained` and `FocusLost` set the focus, and a `KeyDown`, a `Char`, or a `PointerDown` proves the focus: a key press, a character, or a mouse press that reaches the scene sets it true, which recovers a `FocusGained` that was never dispatched while the dev server had the app paused. A release is judged by the events before it: one followed by a `PointerLeave` in the same frame is still a click, and an injected click, led by a `PointerEnter`, lands even as the first event after a real leave. The window starts focused (no event comes when it opens), and `onEnter` reads the pointer from the current frame's `InputSnapshot::pointerInWindow`, since it may have entered while another scene was on. Events move the pointer flag within a frame, and each frame starts from the frame's `InputSnapshot::pointerInWindow` (`WindowPresence::syncPointer()`), which also recovers an enter or a leave that was never dispatched. `update()` reads the same `WindowPresence` and on the frame the answer turns false calls `DrawingSystem::pause()`. A paused tool proposes nothing: it computes no snap, its click verdict proposes nothing, and nothing that follows the pointer draws (the rubber band and the wall band to the pointer, the guides, the snapped-point marker, the labels, the rings, the close ring and the halo, the pending rectangle's fill, outline, and size label, the opening ghost, and an Add or Subtract's trial outline and its reason; `DrawingSystem::pointerPreview()` says which of these would draw, and the render paths read it); the status strip shows the tool's hint and the placed shape's readouts, never a refusal. Placed points and their edges, a Freeform shape's fill, the Rectangle tool's first corner, and a pending press stay; nothing is cancelled and no point is dropped. The next `handleMouseMove`, on the first frame the pointer is with the tool and on the world, resumes it from the pointer. A tool starts paused, until its first move. The rule is the prototype's `pauseTool()` on `mouseleave`, `blur`, and a hidden page. Over the interface the pointer is still with the tool, so the preview holds at its last position on the world. A `--background` launch's window opens behind the others and unfocused, and is driven by injected input, so there the focus does not count, as `Main.cpp` leaves `freezeTicksOnFocusLoss` off for the same launch; `GameContext::backgroundLaunch`, the App's context (`App::setContext`), carries the flag to `GameScene`.
- **Double-click ends a wall chain.** salal's `InputEvent` reports no double-click (no click count), so `GameScene` detects it with one `WallDoubleClick` (`WorldPointer.h`), which holds the time and logical position of the last left release handed to the wall tool. A left release within `doubleClickSeconds` (0.4 s, the colonist roster's `kDoubleClickSeconds`) and `doubleClickDistancePx` (4 logical px, in a straight line) of the previous one, each limit inclusive (`secondClickOfDoubleClick()`), is the second click of a double-click: `WallDoubleClick::release()` answers that it ends the chain, and `GameScene` places no point and calls `DrawingSystem::finishChain()`, as Enter does; with one point or none, `finishChain()` drops the chain with nothing committed and no toast. Any other release is a click. A release under any other tool is a click and forgets the record, and `GameScene` calls `WallDoubleClick::forget()` wherever the chain ends or the pointer's continuity breaks: Backspace, Enter, Esc, a right-click, a tool starting or ending (`DrawingSystem`'s `onToolActive`), and a pause. So a quick click on the same spot after any of them is a first click. The rule is the prototype's: the browser's first click places the final point, the second click (`event.detail >= 2`) places nothing, and the `dblclick` handler commits the chain. A third release starts over (the pair is consumed, as in the roster). The first click is an ordinary click: on the chain's first point it closes and commits the loop, and the second then finds no chain and does nothing; refused, it places nothing and toasts why, and the second still ends the chain, which commits without it. Both values are config (D12's table).
- **A pointer at rest proposes nothing.** Each click with which a tool places something (a Freeform, Add, or Subtract point, a wall chain point, the first included, or an opening) records the tool, the raw pointer's world position, and what the tool holds after it, its point count and the opening placed (`DrawingSystem::lastPlacement_`). Three things clear it: a tool starting or being put away, Backspace, and a move that leaves the raw pointer more than half a screen pixel, at the current zoom, from where it was at the placement (`pointerLeftLastPlacement()`, `kRestTolerancePixels`). So the camera's sub-pixel settling after a pan does not end the rest, a visible glide does, and the rest ends for good when the mouse moves or the camera pans or zooms under a still mouse. A record never carries over to another tool or another start of the same one. One function, `restsOnLastPlacement()`, answers whether the pointer rests on that placement, and `clickVerdict()` alone reads it: at rest, the refusal about the thing just placed proposes nothing (valid, `proposed` false). That is `VerticesTooClose` in the Freeform, Add, and Subtract tools, `SegmentTooShort` for the wall tool's zero-length trial segment, and `OpeningOverlap` for the opening tool. Any other refusal (off buildable ground, unexplored, off the host foundation, a crossing) shows as it would anywhere, a still pointer whose snapped point is valid (an angle step can make it so) proposes and places that point, and a click that closes the shape closes it. Everything else reads the verdict: the strip shows the tool's ordinary hint, nothing draws red, an edit's outline is the placed points' own, the opening tool draws no ghost, the dev view reports `proposed` false, and the click places nothing and toasts nothing. ### D14: Drawing Settings storage versus construction config

Two homes, split by who sets the value.

- **Drawing Settings** (the player): the eight helper switches, Round lengths, Show key guide, and the rectangle grid spacing. They live in `UserSettings` as one member, `drawing`, of type `DrawingSettings` (`apps/world-sim/UserSettings.h`, namespace `world_sim`):

  ```cpp
  struct DrawingSettings {
      bool  angleSteps = false;
      bool  guidesFromShape = false;
      bool  alignToExistingBuildings = false;
      bool  guidesFromWorldAxes = false;
      bool  guideCrossings = false;
      bool  commonLengths = false;
      bool  guideDistances = false;
      bool  angleReadout = false;
      bool  roundLengths = false;
      bool  showKeyGuide = false;
      float rectangleGridSpacingMeters = 1.0F;  // 1.0 or 0.5
  };
  ```

  `DrawingSettings` is the superset the player sees. The engine never includes it (`libs/sim` cannot reach an app header); it takes `construction::DrawingAids`, which holds the same switches minus the display-only ones (`guideDistances`, `angleReadout`, `showKeyGuide`), and `UserSettings::drawingAids()` builds that struct from `drawing`. The display-only switches never enter sim; the drawing code reads them.

  The initializers in the struct itself are all-off placeholders (a 1 m grid); the values come from a `<DrawingSettingsDefaults>` block in `snapping.xml` (`assets::DrawingSettingsDefaults`, one element and one field per setting, with these names), read once when `UserSettings` is first touched. The defaults a new player meets are every helper off, Round lengths and Show key guide on, and a 1 m grid; `assets::DrawingSettingsDefaults`' own initializers hold the same values, and a test keeps the two copies equal. With the helpers off, the Freeform tool's fourth corner is the pointer's, its length rounded; the Rectangle tool draws the square building, and world-axis guides with crossings give the corner lock for a player who switches them on. Drawing Settings last the session and are not saved: each launch starts from the defaults (the interface size, the window's size, and vsync are the settings saved to `settings.json`). The validator checks that `rectangleGridSpacingMeters` is 1.0 or 0.5.
- **The Drawing Settings pane.** `SettingsScene` has a "Drawing Settings" group: the helper toggles in the design spec's order, then Round lengths (its label built from `lengthIncrementMeters`, "Round lengths to 0.1 m"), Show key guide while drawing, and the grid spacing as a two-choice control. Each row has the one-line description from the design spec's table; the "15 degree" in Angle steps' line comes from `angleIncrementDegrees`.
- **Construction config** (the designer): everything in D12's table and D16's look keys. Never shown to the player.
- **Reading them.** `DrawingSystem` builds a `DrawingAids` from `UserSettings::Get().drawingAids()` and keeps it in the snap memo's key and passes it by value in `SnapInput` when the memo misses, and reads the display-only switches from `drawing` itself; the engine never reads `UserSettings`, so tests pass their own `DrawingAids`.

### D16: Guide rendering look

Player-facing behaviour: design spec, Foundations > Snapping and guides, under Look. One rule: solid is geometry, dotted and part transparent is alignment, small solid markers state a fact. A px in this section is a window pixel for everything drawn (strokes, markers, rings, clearances), and none of it scales with zoom; the label text and its plate are in ui px and follow the Interface size, as does the edit reason, by the rule for text drawn in the world ([UI scale setting](../design/ui/ui-scale-setting.md), World text). The one exception is the key guide's legend glyphs (D15), which `drawFeedbackPlan` draws in their component's ui px, look keys included.

- **One helper.** `DrawingFeedback` (`apps/world-sim/scenes/game/world/construction/DrawingFeedback.h`): `planSnapFeedback`, a pure function from the snap result, points, camera, and style to the strokes, rings, arcs, dots, and labels of one frame (tested), and `drawSnapFeedback`, which draws that plan in window px. `planLegendGlyph` and `drawFeedbackPlan` share its stroke helpers and draw routine, and plan and draw the key guide's legend glyphs in ui px (D15). It is the one guide implementation: `DrawingSystem` holds no guide drawing of its own and calls `drawSnapFeedback` in one place, `drawPointerFeedback`, which has three callers: `renderPreview` (the Freeform tool, and Add and Subtract), `renderRectanglePreview`, and `renderWallChainPreview`. It draws after each preview's geometry and above it: the guides, the markers, the labels, and the snapped-point marker all sit over the placed edges, the rubber band, and the vertex dots (and over the wall preview's band). It draws `guideCount` guides whatever the kind (a squared `Edge` or `WallSegment` carries one), each from `from` to `to`, skipping one whose ends are not finite; a stroke or right-angle marker under half a pixel long on screen draws nothing. A second guide whose ends both lie within a pixel of the first's draws no stroke or label of its own, but its right-angle marker draws unless the first marks the same edge, so each distinct edge direction among duplicates gets one marker. A guide's stroke draws only where it lies more than a pixel from the segment being drawn (the previous point to the snapped point); the segment's solid line already shows the rest, and dots that close would bead it (teal beads on red when it is invalid). A guide ends at the snapped point, the segment's end, so its stroke runs from its node to where it first comes within a pixel of the segment, and nothing draws when that is shorter than half a pixel. A guide through the previous point draws no stroke this way, and its right-angle marker still draws; so the angle step's ray draws nothing beyond the segment, a world-axis guide from an older corner that runs on through the previous point is dotted to a pixel short of it and solid beyond, and a guide a fraction of a degree off the segment stops where it comes within the pixel instead of running along the solid line. A guide's distance label draws only when its stroke draws, beside the middle of the part of the stroke on screen (D12).
- **Alignment strokes.** Each guide is a `Primitives::drawPolyline` of its two points with `width = guideWidth`, the guide colour at `guideOpacity`, and `dash = DashPattern{guideDashPx, guideGapPx, 0, DashCap::Round}` for `dotted` (round caps make each 1 px dash a dot), the same with `DashCap::Butt` for `dashed`, no dash for `solid`. The pattern starts at the guide's node (phase 0 at `from`), so the dots don't crawl as the cursor moves. The origin's close-radius ring (three or more points placed) uses the same dash, in `originHaloColor` at that colour's own alpha (so the config sets its opacity), 1.5 px wide (1 px at 0.42 opacity is invisible over grass). It draws only while the close halo does not: once the click will close and the halo is drawn, the halo alone marks the first point, and where the close verdict refuses the click, so no halo is drawn, the ring stays.
- **Markers, solid at `markerOpacity`.** The right-angle marker in screen space: `from`, `from` + the edge direction, and `from` + the unit direction toward `to` go through `toScreen`, the two screen directions are normalised (`edge` and `guide`), and with `size` = `rightAngleMarkerPx` the mark is two 1.5 px lines from `corner + size*edge` to `corner + size*edge + size*guide` to `corner + size*guide`. A right-angle marker whose edge is within about 3 degrees of parallel to its guide draws nothing. A `GuideCrossing` adds a filled dot of radius `guideCrossingDotPx` (3 px), centred on the point and drawn above the snapped-point marker, inside its white dot, so the marker reads as a target; it takes the first guide's colour (its source colour under `bySource`) at `markerOpacity`. Common lengths, in the common-length colour (`guideColor` under `one`, `guideColorLength` under `bySource`): a tick across the segment at the snapped end, 8 px each side, 2 px wide; on each matched edge a 6 px band at 0.22 opacity and, at its middle, two 1.75 px ticks 4 px apart, 6 px each side; the ticks at `markerOpacity`, the bands in the alignment layer, planned before the guides so they draw under them, as the prototype draws its matched edges first. The angle readout, in the shape guide colour at `markerOpacity`: at a corner that is not square an arc 18 px in radius, 1.5 px wide, from the edge toward the previous vertex through the inside of the corner (`cornerAngles`' sweep, drawn with the renderer's `drawArc`); its square corner is the right-angle marker, its legs along the corner's two edges, drawn by the same helper as a guide's, and left out where a perpendicular guide's right-angle marker already sits on that vertex (within a pixel), so one marker stands for both. A corner whose shorter edge is under the arc's 18 px radius on screen draws neither arc nor degrees: an arc wider than its edge reads as noise (the prototype draws it regardless).
- **Labels.** The segment label, 12 px text (bold and in the accent colour when matched): beside the segment's middle, its plate 7 px off it (the text 10 px at an Interface size of 100%) on the side away from the placed points' centre, measured from the previous point in world metres so that along a ray it does not wander with the snapped point's rounding (with the centre within half a pixel of the line, the side facing up the screen, or left when the segment is within about 11 degrees of vertical, where its normal's y is under `kFacingUpMinimumNormalY`, 0.2), when that keeps it at least 40 px from the snapped point, where the pointer sits; otherwise at the snapped end, its plate a fixed 9 px diagonally off it at every Interface size and its text a further plate padding in (the padding follows the Interface size), in the quarter that points most along the segment, of up right, up left, and down left (near-ties go to the first in that order), never the lower right one, where the pointer hangs. There is no segment label while its length rounds to zero (the snapped point on the previous point): there is nothing to measure. Every placement, at the middle and at the end, is judged on a box the width of a "999.00 m" label (or the label's own width, when wider), anchored as the label is (at the end, by its corner nearest the snapped point), and the label draws at its own width inside that box, so under 1000 m a digit added at 10 m or 100 m changes neither whether the label fits a placement nor which one it takes. While Common lengths is on, the box also holds a matched "999.00 m =" label in its bold face, its width and its line height, so the " =" coming or going changes neither either. It keeps off the snapped-point marker (its dot and its ticks, a cross rather than a square, so the end placements fit between the ticks), the close halo while that is drawn, the wall tool's snap-target ring while that is drawn, and a box the preview asks it to keep clear: a rejected Add or Subtract edit's red reason beside the pointer, measured with the same text measure as the labels. Each placement is checked where it finally lands, after any move onto the screen, and one that would cover any of them, or a middle one moved back within 40 px of the snapped point, gives way to the next in order. The end placements sit that far diagonally off the snapped point, or off the close halo's box when the halo is drawn round the snapped point (the click closes on the first point), and off the snap-target ring's box when the ring is drawn. With no clear placement, which happens with the snapped point near the top-left corner of the screen, where only the lower right would fit, with the label squeezed between a screen edge and a close halo drawn off the snapped point (the near-start rescue), or with it squeezed between a screen edge and the reason, it takes the first end placement whose box fits the screen unmoved, even where that covers what it keeps off, and moves the first one just inside only when none fits (then it can sit to the lower right in the top-left corner). That corner lies under the game's top bar, where the drawing preview does not update. When the segment's middle is off the screen, a middle placement is moved inside to the nearest screen edge, and taken only if it is still clear and 40 px from the snapped point there. Sweeps of rays from points across the screen (three screen sizes, zooms from 0.25 to 20, one, two, or six placed points) show this much, and no more: with the snapped point at least 120 px and the previous point at least 100 px from every screen edge, and no close halo or edit reason drawn, the placement changes at most once along a ray, from the end to the middle; and a digit gained at 10 m or 100 m never changes the placement, anywhere (six million checked pairs, no violation). Two cases break the first claim, and both are accepted as rare and cosmetic. With two or more points placed, when the placed points' centre lies almost exactly half a pixel off the segment's line (within about a thousandth of a pixel of the edge of the dead zone), the label can change sides every few centimetres along the whole ray; by a simulation of pointer-placed points that is about one two-point segment in fifty thousand, and no stateless rule avoids it, since any threshold has an edge that rounding can straddle, so removing it would take the label remembering its last side. And more than about a kilometre and a half from the world origin, float rounding of the snapped point on a very short segment can change the end placement once within the first ten centimetres of a ray. Outside that, the label gives way to the screen edge, the marker, the halo, the wall tool's snap-target ring, and the reason, and may change sides more than once and back. Guide distance labels at `guideLabelPx`, in the guide's colour at full opacity (bold and in the accent colour when matched). Bold is the theme's display face, a semibold, since the game's default face has no bold cut. The angle readout's degrees at `guideLabelPx`, `angleReadoutDecimals` places and a degree sign (the default face's own glyph), in the shape guide colour at full opacity, beyond its arc on the inside of the corner (along the corner's bisector) or on the outside (the other way along it). On either side the first spot puts the plate 3 px off the arc: its centre is as far out as puts the plate's nearest point 18 + 3 px out along that direction (the plate's support distance there, its half width and half height, padding included, weighted by the direction's components), so no corner of the plate reaches the arc, at any Interface size. On a bisector along an axis the inside's first spot is the prototype's spot. It is planned after the segment and guide labels and keeps off them, the snapped-point marker out to its ticks, the close halo while it is drawn, the wall tool's snap-target ring, the box the preview keeps clear, its corner's two edges and the segment being drawn, and the arc of every corner that has one when the label is planned, the corners after it included even if one of them later finds no spot, each with its 3 px gap (a disc 21 px in radius, so a plate moved onto the screen never sits against an arc): when a spot would cover one, the label moves out 4 px at a time, at most 48 px beyond the first spot so it still reads as its corner's, each spot moved just inside the screen. The inside is tried first, then the outside, unless the corner's two edges or the segment being drawn cross the inside's first spot, as in a narrow corner, where the outside is tried first. Along a ray of the pointer which side leads changes at most once; the label also changes side when another label takes every spot on its side, which along most rays happens at most once more. When neither side has a clear spot, or the corner itself is off the screen, the corner draws neither its arc nor its degrees, since a bare arc reads as broken; a square corner's right-angle marker is unaffected. Every label sits on a dark plate (the prototype's dark, `#0A0C10` at 0.7 opacity, 3 px larger than the text all round, 3 px corners) with no text halo, since the renderer caps a halo at about a pixel and thin halos read badly over the tan floor. The plate, sized by the font's line height, is the box labels keep apart. A guide label whose plate would leave the screen goes to the other side of its guide, and is moved just inside only when both sides leave it; it sits beside the part of its stroke on screen and shifts no further than that part's ends (D12), and with no clear spot along it, it is dropped. Lengths show `guideDistanceDecimals` places; a guide distance that rounds to zero prints unsigned.
- **The cursor.** The game shows the operating system's cursor at the raw position, so, departing from the prototype on purpose, it draws no raw-pointer ring and no pull line from the raw pointer to the snapped point. It draws the snapped-point marker where the point will go, at full opacity as the prototype does: a white dot of radius `max(4, cursorRadiusPx)` (6 px by default) with a 2.5 px black outline, and four ticks, left, right, up, and down, each from `radius + 5` px (11 px) to 16 px from the point, a 2 px white stroke over a 6 px black one. Off buildable ground (and not closing), or while closing with the close refused, the marker's dot takes the invalid colour, keeping its outline and ticks, in the foundation tools and the wall tool alike; it is the one marker, and no separate dot marks the cursor. With the wall tool snapped to a wall endpoint or foundation vertex (amber, `snapVertexColor`) or to a wall segment or foundation edge (cyan, `snapEdgeColor`), a 2 px snap-target ring is drawn above the marker at 4 px outside its ticks (20 px at the default radius), the same size at every zoom. Whenever the next click closes (an `Origin` result or the near-start rescue close) and the close verdict accepts it, the first-point halo: a ring of radius `max(ticks + 6, originCloseRadiusMeters * pixelsPerMeter / 2)` screen pixels (half the close radius on screen, with the zoom-widened radius from `SnapInput`; the floor, 22 px at the default radius, is its own constant so the halo rings outside the marker's ticks, and is not `originHaloMinRadiusPx`, which floors the catch radius and so the close ring), 3 px wide, in the shape guide colour (`guideColor` under `one`, `guideColorShape` under `bySource`) at `markerOpacity`. While the next click closes, the preview's colour, the halo, the snapped-point marker's dot, the status strip, and an Add or Subtract's outline colour and reason text all show the one pending close, the result of `DrawingSystem::closeVerdict()` kept while the next click closes (the strip reads it directly, the rest through `previewVerdict()`). For a foundation and for Add and Subtract it is the check the closing click runs before it commits (the ring's validation and its whole footprint for a foundation; for an edit, the outline's validation and that it is seen, and for Add the ground it adds, since a Subtract builds nothing): a close the click would commit draws the halo, and the rubber band and fill read valid even when the pointer sits where a point would be refused; a close it would refuse draws no halo, the band and fill read invalid, the marker's dot is red, and the strip and the edit's reason text say why. For the wall tool it is the chain with the closing point added: its ground, and every segment through the check `commitWallChain` gives it (`commitWallSegments`, run on a copy of the world, so each segment is judged against the ones committed before it). A halo means the whole chain gets built; a refused verdict means not all of it will be. The wall click does not run the verdict, and still builds the segments that pass. The verdict's shape part (a foundation's ring validation, the wall chain's segment checks) is kept with the snap while the snap memo holds, since it reads only what the memo's key covers; an edit's outline reads the target's blueprint, so it is validated once per move and shared with the edit preview and the commit; the ground checks run on every move, since they read player visibility and the navigation mesh, which the key does not cover, the cost the placement cursor's own ground check already pays. The picture can lag a world change by a frame, and a commit can still fail after these checks in the rare case the topology refuses it (a toast says so). Otherwise the colour is the point's.
- **Keys.** `assets/config/construction/rendering.xml` `<Preview>`; every size is in window pixels and never scales with zoom, except the label text and its plate, which are in ui px, and the key guide's legend glyphs, which `drawFeedbackPlan` draws with these keys in their component's ui px (D15). Only the text the player reads follows the Interface size: `DrawingFeedbackInput::uiScale` (the scale `renderPreview` gets) multiplies the label text sizes (the segment label's 12 px and `guideLabelPx`) and the plate's padding and corner radius (so a label's text moves out by its padding and the plate keeps its gap: 9 px at the snapped end, 7 px beside a line), in one place (`lookAt` in `DrawingFeedback.cpp`), as `editReason` scales the reason's text and offset. Strokes, dashes, the snapped-point marker and its ticks, the crossing dot, the right-angle marker, the common-length ticks and bands, the angle readout's arc, the close ring and halo, the snap-target ring, the Rectangle tool's grid cross and rings (D13), and every clearance and threshold stay in window pixels, like the preview's own lines and vertex dots, so the guides never outweigh the geometry they align; ratios, angles, opacities, colours, and world lengths don't scale either. The close catch's pixel floor, `originHaloMinRadiusPx`, decides what a click does and is not scaled.

## 4. Phasing

Dependency-ordered epics. Each lands independently testable; later epics consume earlier ones.

```
A. Geometry foundations ──> C. Foundations end-to-end ──> D. Walls ──> E. Rooms
                                                            └──> F. Openings
                                                                 G. Editing & polish

Navigation & pathfinding: own spec, scheduled independently (D5).
Must land before walls ship as player-facing gameplay; blocks nothing above.
```

**A. Geometry foundations.** `libs/geometry`: quantization, predicates, constraint primitives, planar graph + face extraction, arrangement-based booleans, band offsetting + junction trimming. Pure library, no new dependencies, exhaustively unit-tested (shared-edge boolean cases first). Record considered-and-rejected libraries in `library-decisions.md`.

**C. Foundations end-to-end.** ConstructionWorld (foundations only), FoundationTool + SnapEngine + ConstructionValidator + config strip, blueprint lifecycle components, ConstructionSystem goals (clear → deliver → build), StructureRenderer (fill patterns, progress prefix rendering, blueprint style), selection + info panels + adapters, `assets/config/construction/`. At the end: draw a foundation, colonists clear/haul/build it, it renders progressively, it's selectable. No walls yet.

**D. Walls.** Wall graph (vertices/segments/junction splitting), WallTool (chain drawing, snap targets, edge fill via Ctrl+click), band + junction rendering, obstacle publication per the D5 contract (consumed once nav exists), per-segment demolition with refund. Walls don't block movement until the nav epic lands.

**E. Rooms.** Face extraction on built/demolished events, room entities, room-formed toast. (Overlay UI ships with the broader overlay system per the design spec.)

**F. Openings.** OpeningTool, parameter-extended procedural assets (D9), wall-blueprint reservation + retrofit cut tasks, portal publication per the D5 contract.

**G. Editing & polish.** Foundation add/subtract (the in-house ring booleans + re-validation), vertex editing on blueprints, demolish-building cascade, multi-select batch actions, click-cycling refinement.

*G3 as built (foundation Add / Subtract).* The edit is a `ToolKind::FoundationEdit` mode of `DrawingSystem`, not a separate tool class: it reuses the foundation tool's snap, click, close, Backspace, and Esc flow, activated from the foundation panel's Add / Subtract buttons. The drawn polygon is a cutter, so per point it only has to stay simple with spaced vertices (`ConstructionValidator::validateEditPoint`); the foundation rules apply to the *resulting outline*. `ConstructionValidator::validateFoundationEdit` decides everything in one place: a blueprint is editable only while `StructureBlueprint::shapeEditable` holds (nothing delivered, no work, no demolish order) and is then unioned or carved in place (`ConstructionWorld::addToFoundation` / `subtractFromFoundation`, with the mirror entity's manifest, work, and HP re-sized by the same sizing helper spawn uses and sent back to Clearing); a built foundation never shrinks, and an Add onto it becomes an **extension**, a separate blueprint foundation whose ring is the drawn polygon minus the target, linked by `Foundation::mergeTarget` (`ConstructionWorld::commitExtension`). One extension per target at a time, so merges never depend on order. The validator judges the outline the extension's merge will actually produce, and `commitExtension` refuses a ring whose union with the target fails, so `mergeExtension` cannot fail later. When the extension's build completes, the structure-completed callback merges it: the target's ring becomes the union, the extension's walls re-host onto the target (a wall on the old edge stays put and becomes interior), the target entity absorbs the extension's manifest, work, and HP, and the extension entity goes through the deferred-destroy queue. A pending extension counts as a dependent of its target for demolition: plain Demolish and Demolish building both take it down, and the deconstruct cascade gate holds the target until it is gone. Outline checks (`checkOutline`, shared with `validateRing`) run the full closed-shape constraints, the point cap, min/max area, and overlap plus pathing clearance against every other foundation: every vertex of either ring closer than `pathingClearance` to the other must itself touch it (snapped edge to edge, within 2 mm), so touching in one place never excuses a sliver elsewhere. An Add checks buildability only on the ground it adds (`FoundationEditResult::buildsOn`: the extension for a built target, the drawn polygon for a blueprint). A Subtract must also keep each hosted wall's full-thickness band inside the remainder. `/api/dev/foundation-edit` runs the same `DrawingSystem::applyFoundationEdit` the tool's close runs.

## 5. Risks & Open Technical Questions

1. **Junction band geometry.** Clean trimming at 3+ way junctions with mixed thicknesses is the fiddliest geometry in the feature. Mitigation: prototype in `libs/geometry` tests with golden-image cases before renderer integration; naive overlap as a temporary fallback is acceptable for opaque built walls but not translucent blueprints.
2. **Progress-prefix rendering vs. vertex format.** Element-ordered index buffers must coexist with the baked path's per-vertex colors and any per-material batching. If a structure's elements span draw batches, the prefix counter needs to be per-batch. Resolve during C.
3. **Hand-rolled boolean ops.** The riskiest in-house geometry (see D2). Coincident-edge unions are the normal case for Add-mode, not the edge case. Mitigation: exact integer predicates, narrow validated input domain, reject-don't-repair, and the densest test suite in the feature with shared-edge/shared-vertex cases enumerated first.
4. **Sequencing against Goal-Driven Task Generation.** Construction goals are designed for the refactored model. If construction starts first, it temporarily rides the current registry like Haul does. Decision point at the start of C.
5. **Coordinate range.** int64 millimeters is comfortable for any plausible world size; intermediates in predicates use 128-bit math. Confirm MSVC `__int128` story (or use a two-limb helper) in A.
6. **Determinism.** Integer geometry and seeded element emitters are deterministic by design; keep any iteration-order dependence (e.g., unordered_map walks) out of geometry-affecting code paths for multiplayer's sake.
7. **Walls-before-nav window.** Walls can be built in dev before pathfinding exists, but they won't block movement, so any playtesting in that window misrepresents the gameplay. The nav epic must be scheduled before walls are treated as shipped; the D5 contract keeps the two workstreams from blocking each other in the meantime.
8. **Structures vs chunk unload (settled).** Chunks regenerate deterministically on reload and evict their placed entities; player structures cannot regenerate and don't need to: `ConstructionWorld` stays fully resident — structure counts and per-structure data are small. Only derived data (baked meshes, nav tiles, component graphs) unloads with chunks and rebuilds from the graph on reload.
