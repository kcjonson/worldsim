# Include graph

`tools/resolve-includes.mjs` resolves every `#include` under `libs/` and prints a per-library matrix of include counts. It exists to measure layering drift without building anything.

## What it measures

Each include is resolved against the including file's directory (quoted includes only) and then every library's include root, which approximates the build's lookup with every library's root visible to every file. The roots are hardcoded and match CMake as of 2026-10-31; `libs/` itself is a root too, because planet-view exports it. foundation, renderer, app and salal's ui are not in this repo (they come from [salal](https://github.com/kcjonson/salal) through FetchContent), so their four roots, and their four rows, are read from a salal checkout given with `--salal`; their paths print with a `salal/` prefix. Salal's ui goes by `salal-ui`, since worldsim's own ui is still `libs/ui`; its root comes before `libs/`, which answers `ui/` paths with worldsim's ui. A salal file resolves against salal's four roots only, as salal's own build does, and a `theme` file (worldsim's theme, icons and components on salal's ui) against those and its own, since it links nothing else; so a header salal generates (`ui/theme/Tokens.h`, `theme/Tokens.h`) counts as external instead of landing in worldsim's `libs/ui/theme/Tokens.h`. A directory under `libs/` the script doesn't know makes it exit 2, so a new library can't be silently left out, and so does a missing salal checkout or a stray `libs/foundation`, `libs/renderer` or `libs/app`. The first hit decides the destination library; an include that resolves nowhere counts as external (system and vcpkg headers). `engine/assets/` is tallied as its own row, `engine(assets)`. game-systems has no row because it has no includes (one placeholder source).

Cells are counts of `#include` lines, with self-includes on the diagonal. The script prints an all-files matrix and a production-only matrix; a file counts as test or bench when its name contains `.test.` or `.bench.` or ends in `TestWorld.h` or `TestSupport.h` (engine's two test-support headers). After the matrices it lists ambiguous resolutions (a header name present in more than one library), includes that cross the layering, the engine -> ui coupling surface, and what engine's `app/` (the bridge between worldsim's ui and salal's app, until worldsim moves onto salal's ui) includes from `libs/`.

The layering it reports against follows the per-library "Depends on" lists in [monorepo-structure.md](./monorepo-structure.md): foundation at the bottom; geometry and renderer above it; ui and world above renderer; planet-view and game-systems above world; salal's ui (`salal-ui`) above renderer and salal's app above it, neither including anything of worldsim's; theme above salal's ui; engine on top, allowed to include anything. planet-view's row is inferred, since that doc predates it. Violations are reported, not enforced: the script exits 0 either way.

## Running it

```
node tools/resolve-includes.mjs
node tools/resolve-includes.mjs --salal path/to/salal
node tools/resolve-includes.mjs --root path/to/another/checkout
```

`--root` defaults to the repo the script lives in. `--salal` defaults to `build/_deps/salal-src`, which a configure against the pinned tag populates; a build configured with `-DFETCHCONTENT_SOURCE_DIR_SALAL` has nothing there, so pass that checkout. Output order is fixed (directories walked by name, rows sorted by file and line), so two runs on the same tree diff clean.
